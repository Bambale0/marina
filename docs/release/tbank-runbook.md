## Настройка эквайринга

- Личный кабинет: https://business.tbank.ru/
- Документация Init: https://developer.tbank.ru/eacq/api/init
- Исходящий API: POST `https://securepay.tinkoff.ru/v2/Init`
- GET-проверка: POST `https://securepay.tinkoff.ru/v2/GetState`
- Плановый URL входящего подписанного уведомления (`NotificationURL`): `https://marina.xn--e1aikcel5c5a.online/api/webhooks/tbank`
- Для уведомлений Т-Банка возвращать HTTP 200 с **буквальным текстом `OK`**.

Реальные ключи никогда не вносить в Git, PR, параметры командной строки, логи, тесты или чат. Хранить только в защищённом `/etc/marina.env` (права `0600`).

После завершения настройки терминала, его кассы/чеков и проверки API на разрешённом тестовом контуре применить:

```dotenv
PUBLIC_URL=https://marina.xn--e1aikcel5c5a.online
ENABLED_PAYMENT_PROVIDERS=tbank,lava
PRIMARY_RUB_PROVIDER=tbank
TBANK_TERMINAL_KEY=<выданный банком TerminalKey>
TBANK_PASSWORD=<выданный банком Password>
TBANK_API_URL=https://securepay.tinkoff.ru
```

При необходимости передачи состава фискального чека (значения не назначать произвольно, согласовать с банком/кассой):

```dotenv
TBANK_RECEIPT_TAXATION=
TBANK_RECEIPT_TAX=
TBANK_RECEIPT_PAYMENT_OBJECT=
```

Три фискальных параметра включаются только вместе. Если терминал требует дополнительные реквизиты чека, подтвердить схему с банком **до** приёма реальных денег. `TBANK_PASSWORD` — исходный секрет подписи, никогда не отдавать клиенту. `NotificationURL` не должен перенаправлять запросы, скрывать POST или попадать под ручную CAPTCHA/WAF-проверку.

## Жизненный цикл заказа

1. Публикуемая цена фиксируется целым количеством копеек в снимке заказа в SQLite; выбор Tbank применяется **к новым** рублёвым счетам. Ранее созданные Lava-заказы не переопределять.
2. Попытка платежа сохраняется **до** вызова `Init`. `OrderId` — внутренний неизменяемый ID попытки. Повторный POST `Init` при timeout/неопределённом ответе запрещён; открыть `invoice_creation_uncertain` для ручного поиска по `OrderId`.
3. Входящие webhook проходят проверку `Token` и `TerminalKey`. Статус `AUTHORIZED` не означает финальное поступление.
4. Для подписанного `CONFIRMED` сохраняем событие; отправляем серверный `GetState`; сравниваем `PaymentId`, `OrderId`, `TerminalKey`, копейки и статус. Только затем в той же SQLite-транзакции выполняется `commerce.confirm`, создаётся `receipts` с уникальными `(provider, charge)` и единичное исполнение заказа.
5. Несовпадение суммы, дубль, неизвестная попытка, запоздалое подтверждение или нечёткий статус — сверка, без безусловной выдачи. Возвраты/chargeback не обнуляют права пользователя автоматически.
6. Логи не содержат подпись, пароль, Telegram bot token или сырое тело provider response. Отслеживать `attempt_id`, `payment_id`, `order_id`, latency и статус подтверждения (без секретов).
7. Для кошелька Нейро-коинов `NEUROCOINS_TBANK_ENABLED=1` включать **отдельно**, только после согласования легальности внешней оплаты цифровых товаров и проверки самостоятельного веб-кабинета: `/wallet` не является checkout внутри Telegram.
8. При неготовом Tbank оставлять `PRIMARY_RUB_PROVIDER=lava` и `ENABLED_PAYMENT_PROVIDERS=lava`. Не включать автоматический слепой fallback после неопределённого `Init`: он рискует создать два оплаченных счёта.

## Smoke/acceptance до включения трафика

- [ ] Новый магазин и тестовый/боевой терминал настроены, HTTPS callback общедоступен.
- [ ] Финальная схема чеков и тип терминала сверены с Т-Банком.
- [ ] Подписанный тестовый `CONFIRMED` после `GetState`: ровно одна квитанция и одно право/зачисление.
- [ ] Повторный webhook, второй worker, невалидный Token, другой `OrderId`, сумма или `TerminalKey` не создают дополнительные права.
- [ ] Неуспешный Init и timeout не запускают повторный денежный POST.
- [ ] Проверены возвраты, `AUTHORIZED`, поздняя оплата, reconciliation, целостность БД и резервная копия перед переключением.
- [ ] Telegram `/start`, `/menu`, профиль, консультация, PDF, внешний `/wallet` и исходящие уведомления проходят реальный smoke.
- [ ] Проверен rollback **конфигурации для новых платежей** без переписывания уже оплаченных попыток.

Изменение `PRIMARY_RUB_PROVIDER` само по себе не переводит существующий платёж: provider закреплён в снимке заказа.
