# Эксплуатация предварительной версии

## Сервер

Процессы `marina-web`, `marina-poll`, `marina-worker` запускаются systemd от отдельного пользователя marina. Таймер `marina-backup.timer` создаёт ежедневную копию. Исходники конкретного выпуска расположены в `/opt/marina/releases/<SHA>`, текущий каталог — symlink `/opt/marina/current`. База и файлы — `/var/lib/marina/marina.sqlite`. Секреты — `/etc/marina.env` с правами 0600; в рабочем каталоге разработки также есть исключённый из Git `.env`.

```bash
systemctl is-active marina-web marina-poll marina-worker marina-backup.timer
curl --fail http://127.0.0.1:8075/health
systemctl show marina-poll -p NRestarts -p ActiveState -p SubState
```

API слушает только 127.0.0.1:8075. Другие приложения и виртуальные хосты сервера не перенастраиваются. Админка работает внутри Telegram и не зависит от `PUBLIC_URL`. HTTPS-домен, `PUBLIC_URL`, виртуальный хост по deploy/nginx.conf.example и `TRUST_PROXY=1` нужны для публичных redirect/webhook, в том числе Lava.top. Polling продолжается без входящего Telegram webhook. Не запускать два потребителя getUpdates одного токена.

Администратор задаётся только `ADMIN_TELEGRAM_IDS`. После изменения окружения перезапустить процессы; аккаунт получает роль по allowlist при следующем обращении к боту. Токен бота заменяется в окружении; приложение не показывает его в интерфейсе. `/id` показывает ID, `/admin` открывает нативное административное меню Telegram, `/queue` показывает очередь специалиста, `/material` начинает загрузку текстового исходника в черновик. `/login` не выдаёт одноразовый код и сообщает, что Mini App не используется. Все административные callback-кнопки повторно проверяют allowlist и серверную роль.

## Lava.top — единственный активный провайдер

Интеграция использует Invoice API v3 и хранит секреты только в `/etc/marina.env`:

```text
LAVA_API_KEY=<исходящий ключ API>
LAVA_WEBHOOK_SECRET=<отдельный ключ входящего webhook>
PUBLIC_URL=https://<публичный-адрес>
ENABLED_PAYMENT_PROVIDERS=lava
DEV_TRIPWIRE_BYPASS_PAYMENT=0
```

`ENABLED_PAYMENT_PROVIDERS=lava` включает только Lava.top. Stars отключён для новых покупок; его исторические входящие события и возвраты сохраняются. Prodamus и ЮKassa не подключены. Пустое значение переменной отключает все новые платёжные маршруты; readiness-проверка отклоняет его. В кабинете Lava.top webhook направляется на `PUBLIC_URL/api/webhooks/lava` и передаёт `LAVA_WEBHOOK_SECRET` в `X-Api-Key`. Не выводить значения ключей в журнал, административный интерфейс или команды проверки.

`DEV_TRIPWIRE_BYPASS_PAYMENT` — отдельный временный режим для проверки предложения до появления цены и Lava offer. Он показывает «Принять / Отменить» и выдаёт PDF без заказа и оплаты. Не включать его в коммерческой среде; после настройки тарифа выключить и проверить настоящий платёжный путь.

Задержка предложения после результата хранится в поле `tripwire_delay_seconds` каждой опубликованной возрастной версии сценария и видна в разделе `/admin` → «Трипваер». Для действующего сценария требуется 180 секунд от фактической доставки результата. Изменять её нужно новой версией сценария с причиной, утверждением и публикацией; уже начатое прохождение сохраняет прежний снимок.

Платёжные события приходят в плоском camelCase-формате, а `refund.success` и `chargeback.initiated` — в snake_case envelope с `event_id`, `event_type`, `created_at` и `data`. Последние сохраняются один раз по `event_id` как задача сверки; они не отзывают клиентское право автоматически без утверждённой политики.

В разделе «Трипваер» администратор открывает опубликованную оферту и создаёт отдельную версию правил разовой покупки PDF, связанную с этой офертой. Затем создаёт/публикует PDF-материал и тариф `service=guide` с выбранной ценой в копейках, `currency=RUB`, `material_id`, `age_group`, `web_sales_approved=true` и фактическим `lava_offer_id`; после этого связывает тариф с новой редакцией сценария. Цена, offer ID и срок расчёта не имеют значений по умолчанию. При замене или архивации оферты новые покупки блокируются до публикации новой редакции правил со ссылкой на текущую оферту. Для проверки использовать разрешённый тестовый платёжный контур Lava.top. Success redirect не считать оплатой: основание выдачи — аутентифицированный webhook и успешная серверная GET-сверка счёта.

Перед включением проверить без раскрытия значений: наличие обоих ключей, HTTPS `PUBLIC_URL`, опубликованные и связанные сценарий/тариф/PDF, доступность webhook, один платёж → одно право → одна доставка. При неопределённом POST не создавать счёт повторно вслепую; использовать сопоставление и GET-сверку из административной истории.

## Выпуск и откат кода

Автодеплой предварительной версии выполняет `marina-autodeploy.timer` примерно раз в пять минут. Он использует отдельный checkout `/opt/marina/autodeploy-source` и рассматривает только текущий `develop`. Установка разрешается после завершившегося успешного `Checks` с событием `push` для точного SHA; PR-проверка, чужая ветка, старый успешный запуск и ожидающая повторная проверка не дают разрешения. Перед установкой повторно сверяется удалённый `develop`; более новая установленная версия не откатывается. Репозиторий публичный: GitHub-токен и входящий webhook не требуются.

Первичная установка таймера: после успешного CI подготовленного PR установить его `scripts/autodeploy.py` как `/opt/marina/autodeploy.py` с правами 0700 и две единицы `deploy/marina-autodeploy.*` в systemd, затем выполнить `systemctl daemon-reload` и `systemctl enable --now marina-autodeploy.timer`. После слияния PR в `develop` дождаться CI этого merge-коммита. `systemctl start marina-autodeploy.service` запускает ту же автоматическую проверку сразу; статус — `systemctl status marina-autodeploy.service`, журнал — `journalctl -u marina-autodeploy.service`.

Ручные и автоматические выпуски нового скрипта используют `/run/lock/marina-deploy.lock`. Подготовка venv происходит до остановки процессов. Перед изменением данных три процесса останавливаются, создаётся резервная копия SQLite, а `publish_tripwire_delivery.py` публикует точные тексты выдачи четырёх возрастов через административное версионирование. Тексты поставляются из «ДЛЯ БОТА.docx» в `docs/content/tripwire-delivery-20261106.json`; публикация меняет только `success_text` и `guide_filename`, сохраняя остальной контент и исторические снимки. Маркер `/var/lib/marina/content/tripwire-delivery-publication-20261106.json` делает эту миграцию однократной: последующие ручные правки администратора не перезаписываются при каждом выпуске.

После переключения проверяются `/health` и каждый из трёх процессов. Только после этого обновляется `deployed-commit`. При ошибке активируется прежний каталог кода и восстанавливается запуск процессов; база не подменяется старой копией. Неиспользуемый каталог кода, созданный неудачной попыткой, удаляется только после проверки его SHA и отсутствия активной ссылки на него; следующий запуск может повторить подготовку. Действующий выпуск и `/var/lib/marina` не удаляются. Независимые старые ручные скрипты, которые ещё не используют блокировку, не следует запускать одновременно с таймером.

1. Проверить тесты и состав конкретного коммита; сохранить результаты в протоколе.
2. Проверить `/etc/marina.env`, права пользователя и свободное место; секреты не выводить.
3. `sudo scripts/deploy.sh <SHA>` создаёт отдельный каталог и venv, устанавливает закреплённые зависимости, создаёт резервную копию до запуска миграций, переключает symlink и перезапускает процессы.
4. Проверить `/health`, все процессы, polling и очередь. Сам факт ActiveState=active не доказывает прохождение клиентского сценария.

Для отката остановить `marina-poll` и `marina-worker`, переключить current на предыдущий проверенный каталог и перезапустить три процесса. Не подменять базу старой копией при уже принятых после неё платежах. В версии 0.1 изменения схемы добавляют таблицы и индексы; ранее развёрнутый preview не удаляет неизвестные таблицы. Иные миграции требуют отдельного плана совместимости. Перед восстановлением БД сохранить текущую копию и сверить внешние поступления за интервал восстановления.

Переход в main требует отдельного разрешения владельца на конкретный результат согласно CONTRIBUTING.md. Развёртывание разрешённой здесь предварительной polling-версии не отменяет это требование.

## Резервная копия и восстановление

```bash
cd /opt/marina/current
# В окружении должна быть DATABASE=/var/lib/marina/marina.sqlite
.venv/bin/python -m marina.cli backup --path /var/lib/marina/backups/manual-<timestamp>.sqlite
.venv/bin/python -m marina.cli verify --path /var/lib/marina/backups/manual-<timestamp>.sqlite
```

Используется SQLite online backup, а не копирование открытого WAL-файла. Копия включает BLOB. Перед пробным восстановлением скопировать backup в отдельный каталог, проверить integrity_check и foreign_key_check, запустить приложение с DATABASE этого каталога, сравнить записи/связи/файлы с backup. Не подключать к восстановленному стенду polling и реальные платежи. Проверки на временных данных дополнительно воспроизводят связь аккаунт → заказ → исполнение → право и сохранённые файлы.

Копии на этом же сервере защищают от ошибки приложения, но не от потери сервера. Шифрование диска, внешнее резервирование, сроки жизни backup и удаление данных из старых копий должны быть отдельно утверждены и настроены до коммерческой эксплуатации. Автоматическое внешнее резервирование не заявляется выполненным.

## Типовые ситуации

| Ситуация | Действие |
| --- | --- |
| Telegram недоступен | Результаты остаются в кабинете; проверить outbox, историю попыток и повторить допустимую доставку. Не создавать заново заказ |
| ИИ недоступен | Открыть отчёт, написать новую редакцию вручную, утвердить её и собрать PDF; исходный срок сохраняется |
| Неопределённый Lava checkout | Не повторять POST вслепую. Найти внешний счёт в кабинете Lava, сопоставить ID через административную операцию, выполнить GET-сверку |
| Неопределённый возврат Stars | Не повторять денежный запрос вслепую. Проверить refunded_payment/историю провайдера и задачу сверки; клиентское право не переписывать без основания |
| Пришла вторая оплата | Сохранены оба поступления, исполнение одно. Разобрать задачу сверки; поддержан полный Stars refund, частичный/другой маршрут не имитируется |
| Клиент оплатил поздно | Поступление учтено, заказ paid_review. Применить утверждённую политику вручную; нельзя выставить оплату или новые условия редактированием суммы |
| Просрочен PDF/разбор | Очередь сохраняет due_at. Причина/компенсация оформляются отдельной записью/правом; смена статуса не убирает факт просрочки |
| Специалист отсутствует | Опубликовать operations policy с pause_sales; принятые обязательства продолжают отображаться |
| Истёк срок медиа | Планировщик создаёт retention_task после закрытия услуги. Администратор удаляет файл с причиной; активные обязательства блокируют удаление |
| Пришёл запрос полного удаления аккаунта | Принять запрос в очередь, применить утверждённую политику. Автоматическое стирание анкет, финансовых фактов и backup в этой версии не реализовано; не отмечать такой запрос выполненным по одному статусу |

## Условия перед продажами

Проверить реальный сценарий Lava.top с разрешёнными тестовыми средствами, утвердить тарифы, семейные денежные примеры, начало периода во время trial, возвраты, сроки и последствия отмены/переноса встречи, правила хранения и действия при просрочке. Затем специалист загружает и утверждает фактическую методику, видео и программу курса. Синтетические данные тестов не используются как методический пакет.

## Сохранение сессий и ускоренная проверка администраторов — 07.11.2026

На сервере требуется пакет redis-server. deploy.sh устанавливает отдельный unit
marina-redis и приватный каталог /var/lib/marina/redis (marina:marina, 0700).
Задать REDIS_URL=unix:///var/lib/marina/redis/redis.sock?db=0 в /etc/marina.env.
Сервис использует Unix socket без TCP, AOF и appendfsync everysec.
Проверка: systemctl is-active marina-redis; redis-cli -s
/var/lib/marina/redis/redis.sock PING (от marina или root).

SQLite остаётся авторитетным реестром, поэтому сбой Redis не завершает сессии,
а старые Redis-записи не отменяют блокировку, отзыв и исходный срок входа.
Диалог и callbacks сохраняются в SQLite; перед обновлением нужна обычная
проверенная резервная копия. При откате кода можно оставить Redis работающим.

Мостики после PDF для текущего ADMIN_TELEGRAM_IDS идут через 15/30/45 минут,
для клиентов — по прежнему снимку 24/48/72 часа. Срок купона остаётся исходным.
Чтобы ускорить уже ожидающие админские касания, остановить worker и вызвать
marina.admin_followup_migration.migrate(app, reason) с рабочим окружением.
Повторный вызов идемпотентен, отменённые/отправленные сообщения не возобновляет.
Протокол: admin-followups-sessions-20261107.md.
