# Кошелёк «Нейро-коины» — проектирование и выпуск

## Статус

Feature-ветка `feature/neurocoins-wallet-20261114`. **Продажи в рабочем боте не включены.** Два независимых флага по умолчанию выключены:

- `NEUROCOINS_LAVA_ENABLED=0` — создание счетов пополнения через Lava.top на самостоятельной внешней веб-поверхности;
- `NEUROCOINS_BOT_SPEND_ENABLED=0` — покупка онлайн-занятия монетами прямо в Telegram. Нельзя включать без проверки правил платформы для конкретного типа услуги.

В этом модуле **нет Telegram Stars**, их начисления, обмена или покупок. Наличие исторической поддержки Stars в других модулях не изменено.

Для продажи цифровых товаров и услуг *внутри Telegram* правила платформы требуют Stars даже при наличии отдельного сайта. См. https://core.telegram.org/bots/payments-stars и https://telegram.org/tos/bot-developers. Lava-пополнение предусмотрено только на **независимой внешней поверхности** после проверки категории услуги, договора и допустимости этого сценария. Перед активацией требуется утвердить формат онлайн-занятий, оферту, порядок возврата и работу платёжного сайта. Простое поле `surface=external_web` — метка запроса, а не доказательство того, с какого устройства/сайта начата продажа; отдельно проверить доступ и способ запуска покупки.

## Денежная модель

**1 Нейро-коин соответствует 1 ₽** стоимости услуги. Например, опубликованный пакет номиналом `N` монет оплачивается **`N × 100` копеек** через Lava.top. Утверждённые администратором пакеты задают `coins`, `title` и `lava_offer_id`; стоимость занятия задаёт `services[id=online_lesson].coins`. В коде нет изменяемых цен, внешних offer ID и скидок.

Нейро-коины не являются банковским счётом, не переводятся между пользователями, не доступны для обмена на рубли или вывода. Принимать юридическое решение о предоплате и возвратах нужно до включения продаж.

Новая таблица `neurocoin_ledger` — append-only журнал с ключом `UNIQUE(source, reference)`. Текущий остаток = `SUM(delta)` только по владельцу. Все финансовые изменения выполняются в SQLite `BEGIN IMMEDIATE`, в целых монетах, без float. Списания не могут уйти в отрицательный остаток, кроме отдельного подтверждённого внешнего возврата/chargeback, который требует последующей сверки и возможного отрицательного остатка. Бонусные админ-корректировки также имеют ключ и причину аудита.

## Настройка тарифов через админку

Создать policy с `type=neurocoins`. Поля:

| Поле | Смысл |
| --- | --- |
| `enabled` | Включён ли опубликованный список тарифов (bool) |
| `currency` | Только `RUB` |
| `terms` | Утверждённые условия использования монет, возвратов и услуг |
| `quote_ttl_seconds` | Срок счёта в секундах |
| `packages` | Массив `{id, title, coins, lava_offer_id}` |
| `services` | Массив `{id:"online_lesson", title, coins}` |

Нужны `draft → approve → publish` с проверкой полей. `lava_offer_id` должен соответствовать реально опубликованному offer Lava.top с допустимой ценой по API. Список пакетов, коэффициент 1:1, тип услуги, правила возврата и согласие владельца фиксируются до релиза. Не вводить тарифы наугад.

## Платёжная цепочка: сначала пополнение, потом покупка

1. На отдельной разрешённой внешней странице клиент выбирает пакет и, при необходимости, подтверждённую запись на онлайн-занятие. `POST /api/wallet/topups` с `package_id`, `booking_id` (необязательно), `surface:"external_web"` и уникальным `key` создаёт **pending**, без начисления.
2. Через `POST /api/orders/{id}/checkout` передаётся email, создаётся единственная `payment_attempt`, которая обрабатывается фоновым `invoice.create`. Повторный POST не создаёт нового счёта. Состояние, URL готовой оплаты и остаток доступны владельцу по `GET /api/wallet/topups/{id}`. Для `uncertain` нужна сверка, не новый POST.
3. Lava.top подтверждается **только** штатным подписанным webhook и проверочным серверным `GET /api/v1/invoices/{provider_id}`. Сверяются `id`, `currency=RUB`, сумма в копейках, состояние `completed` и уникальность `(provider,charge)`.
4. В **одной транзакции** фиксируются receipt, `+coins` в ledger и, при привязанной **всё ещё доступной** записи, `-coins` и `booking.paid`. Повтор webhook не меняет ни баланс, ни заявку.
5. Если запись отменена, уже оплачена или не соответствует условиям — весь оплаченный пакет сохраняется на балансе; автопокупка пропускается с audit-событием. Цена занятия берётся из снимка на момент выставления счёта, а не из изменённого тарифа.
6. Для явного списания ранее накопленных монет используется `POST /api/wallet/bookings/{id}/pay`, только при отдельном разрешении покупки внутри Telegram. Само по себе наличие монет не создаёт повторной услуги.
7. Кнопка «Мой кошелёк» показывает `GET /api/wallet`: реальный остаток, последние 50 операций, тарифы, если опубликованы. Бот **не** отправляет URL Lava-пополнения и не создаёт Lava-счета.

### Отмена и возвраты

Отмена оплаченного монетами занятия создаёт `reconciliation` `neurocoins_booking_cancelled`, а не автоматическое зачисление монет. Специалист после проверки условий принимает отдельное решение через `POST /api/admin/wallet/bookings/{id}/refund` с обязательной причиной. Повтор операции не зачисляет повторно.

Подтверждённые возвраты или chargeback Lava требуют авторитетного внешнего подтверждения/сверки; автоматическая обработка возвратов Lava в этой feature-ветке **не реализована**. `refund_topup` — внутренний примитив для будущего аутентифицированного пути. Не связывать его с непроверенным пользовательским запросом.

## Ключевые API

- `GET /api/wallet`: остаток и история текущего владельца;
- `POST /api/wallet/topups`: создание пополнения только при включённом **внешнем** Lava-контуре;
- `GET /api/wallet/topups/{id}`: owner-only статус/URL;
- `POST /api/orders/{id}/checkout`: штатная очередь создания внешнего счёта, email;
- `POST /api/wallet/bookings/{id}/pay`: прямое списание монет только при отдельном включении;
- `POST /api/admin/wallet/{owner}/adjust`: корректировка с ключом и audit;
- `POST /api/admin/wallet/bookings/{id}/refund`: согласованный возврат монет по отменённому занятию.

## Границы тестов и релиза

Автотесты применяют **временную SQLite** и искусственные ответы HTTP-провайдера; реальные средства не перемещают. Обязательные сценарии: уникальный счет, duplicate webhook, mismatch receipt, параллельные списания, отмена во время ожидания оплаты, вручную подтверждённый возврат, разграничение владельцев, маскировка платёжной ссылки внутри Telegram, отказ при неразрешённой поверхности.

Перед коммерческим включением требуется реальная тестовая/низкорисковая оплата у Lava.top с проверкой суммы и offer, signed webhook, журналом correlation IDs, сверкой возвратов, договором и отдельной внешней страницей оплаты. Разрешение на production-покупки **не вытекает** из зелёного CI.
