# Инструкции для работы в Marina

## Обязательные правила владельца

1. **Все сущности продукта управляются через админку.** Новая сущность или бизнес-настройка требует строки в `docs/planning/admin-matrix.md`, административного UI/API, допустимых операций и аудита. Эпик без этого покрытия не завершён.
2. **Изменения сначала попадают в `develop` через рабочую ветку.** Создавать `feature/<epic>-<task>`, `fix/<epic>-<task>` или `docs/<topic>` от актуального `develop`; открывать PR в `develop`.
3. **`main` — только после явного разрешения владельца.** Не создавать, не менять, не сливать и не включать автоматическое слияние в `main` без отдельного разрешения на конкретный подготовленный результат. Общее поручение реализовать эпик или согласование плана таким разрешением не является.
4. При пустом репозитории первый коммит создаётся в `develop`. Если инструмент не позволяет это сделать, не инициализировать `main` в обход правила; сохранить работу и сообщить конкретное ограничение.

## Источники требований

- Последние прямые решения владельца имеют приоритет.
- `docs/planning/developer-plan.md` — продуктовые правила и границы.
- `docs/planning/epics/E00.md` … `E13.md` — подробная декомпозиция.
- `docs/planning/admin-matrix.md` — обязательное покрытие админки.
- `docs/planning/decisions.md` — открытые решения и условия публикации.
- `CONTRIBUTING.md` — ветки, приёмка и выпуск.

Если документы противоречат друг другу, исправить противоречие по явному решению владельца; не выдавать проектное предложение за согласованное правило.

## TDD

Процесс основан на `Bambale0/.agents/skills/grilling` и `skills/tdd`, прочитанных при подготовке спецификации. Использовать один наблюдаемый сценарий за раз: **RED → минимальная реализация → GREEN → рефакторинг**. Проверять публичное поведение, а не устройство реализации. Подменять внешние границы; конкурентные изменения денег и прав проверять с настоящими транзакциями тестовой БД. Не писать заранее весь набор падающих тестов продукта.

Для документационных правок достаточно проверить содержание, ссылки и согласованность. Не создавать продуктовые тесты ради текста. В отчётах различать запланированную приёмку и реально выполненные проверки.

## Инварианты продукта

- Сервис не ставит диагнозы. Методики, пороги и содержательные рекомендации утверждает специалист на основании выбранных источников; нельзя выдумывать их для заполнения интерфейса.
- ИИ использует текстовый контекст. Клиентские видео/аудио изучает специалист. PDF выпускается только после утверждения конкретной редакции.
- PDF: 48 часов после оплаты. Разбор: 48 часов после оплаты и полного комплекта, явно отправленного специалисту. Клиент: 24 часа на одно уточнение; специалист: 48 часов на ответ.
- Trial: 72 часа один раз на аккаунт с первого запуска занятий. Профили детей не перезапускают trial.
- Подписки отдельные на детей. Ступени скидок 0/3/5/8% считаются по всему учитываемому составу семьи; порядок выбора строк корзины не определяет скидку.
- Цены и периоды задаются администратором; примерные цены и неутверждённые 30 дней не являются начальными тарифами.
- Возврат на страницу успеха не подтверждает оплату. Выдача результата/прав идемпотентна; вторая оплата сохраняется и разбирается отдельно.
- Управление историческими фактами — через версии, проверяемые переходы, сверку и компенсирующие записи. Нельзя переписывать сумму подтверждённого платежа, использованный trial, прежние ответы или аудит.
- Опубликованные настройки не меняют уже принятые обязательства. Секреты не помещать в Git, интерфейс чтения или логи.

## Готовность изменения

Сценарий реализован и проверен, админка покрыта, документация и миграции согласованы, ограничения названы, PR направлен в `develop`. Публикация планов и закрытие PR с документацией не закрывают эпики реализации. Формальную защиту веток нельзя считать включённой только потому, что правило написано в документации.

# Порядок разработки и выпуска

## Ветки

| Ветка | Назначение | Порядок изменения |
| --- | --- | --- |
| `feature/<epic>-<task>` | Один рабочий срез продукта | Создать от актуального `develop`, затем PR в `develop` |
| `fix/<epic>-<task>` | Исправление наблюдаемой ошибки | Воспроизводящий тест, исправление, PR в `develop` |
| `docs/<topic>` | План, правила, содержательная документация | Проверка содержания и ссылок, PR в `develop` |
| `develop` | Интеграция готовых изменений и проверяемый результат | Слияния рабочих PR после применимых проверок |
| `main` | Разрешённая владельцем версия | Отдельный PR из `develop` и явное разрешение владельца на этот результат |

Правило владельца: сначала рабочая ветка и интеграция; только после разрешения — `main`. Разрешение выполнить задачу, согласие с рекомендацией и разрешение слить PR в `develop` не означают разрешение на `main`. Не включать auto-merge в `main`; не обходить правило прямым push, изменением ref, cherry-pick или первичной инициализацией.

Если репозиторий пустой, первый коммит создаётся в `develop`. `main` создаётся только при первом разрешённом выпуске. Наличие `main` в метаданных как предполагаемой default branch не означает наличие ветки или согласие на запись в неё.

Эти правила документируют процесс. Серверная защита GitHub/rulesets проверяется и настраивается отдельно в E13; её наличие нельзя заявлять без проверки. Не ослаблять уже действующую защиту, чтобы провести слияние.

## Одна задача

1. Прочитать `AGENTS.md`, эпик и относящиеся строки матрицы админки. Проверить реальные зависимости и открытые решения.
2. Выбрать один проверяемый результат для клиента и специалиста. Описать приёмку через публичное поведение.
3. Для изменения поведения: сначала RED на конкретном сценарии, затем минимальный GREEN, затем рефакторинг. Денежные гонки проверять на тестовой БД, внешние API — на границе адаптера.
4. Реализовать административные операции для затронутых сущностей, аудит и допустимые переходы. Сущность без админского управления не считается готовой.
5. Обновить спецификацию, условия публикации и применимые примеры. Исторические факты и уже принятые обязательства не переписывать.
6. Открыть PR в `develop`: зачем изменение, что теперь работает, как проверено, что ещё ограничено. Ссылаться на эпик и номера задач.
7. Проверить фактическую базовую ветку и состав PR перед слиянием. Не закрывать весь эпик по одному документационному PR.

Для исправлений только в документации не нужны фиктивные тесты приложения: достаточно содержательной проверки, корректности ссылок и структуры. Не запускать расширенные проверки без конкретного риска или установленного условия приёмки.

## Готовность эпика

- Все согласованные задачи и критерии приёмки реализованы; непубликуемые части явно обозначены.
- Администратор может обслужить сценарий без штатных обращений к SQL/разработчику.
- Все новые сущности и настройки отражены в матрице; права проверяются на сервере.
- Сохранены версии методик, тарифов, материалов и условий; опасные операции имеют проверку и историю.
- Реально выполненные проверки и демонстрация записаны отдельно от будущих сценариев.
- Документация, UI и API описывают одинаковое поведение; условия запуска соответствующей функции выполнены.

## Подготовка выпуска в main

Сначала подготовить конкретный результат: PR `develop → main` (если `main` уже существует), список изменений, состояние проверок, миграции, план отката и нерешённые ограничения. Только затем получить явное разрешение владельца. В описании разрешения указать PR/коммит и границы выпуска. Если после согласования содержательно изменился результат, разрешение перепроверяется применительно к новому содержимому.

До первого разрешения не создавать `main` только ради открытия PR. Подготовить обзор коммита `develop` и доступные материалы; после разрешения выполнить согласованный первый выпуск. Слияние и deployment — разные операции: публикация в среду также должна соответствовать объёму поручения.

## Условия работы с материалами

В Git хранить спецификации и обезличенные тестовые примеры. Клиентские анкеты, детские медиа, персональные результаты и секреты интеграций принадлежат защищённым данным приложения. Методические материалы использовать по выбранным условиям и с утверждением специалиста. Содержательная готовность материала не выводится из зелёных технических тестов.
