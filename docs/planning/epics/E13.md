# E13. Приёмка, выпуск через develop и эксплуатация

**Статус:** запланировано; документ не подтверждает работающий продукт, CI или публикацию.  
**Результат:** разработчик передаёт конкретную проверенную версию с понятным составом, готовой админкой и способом восстановления.  
**Зависимости:** E00–E12 в объёме функций конкретного выпуска; неопубликованные функции сохраняются в плане.

## Объём и правило веток

Каждая работа начинается в feature/docs/fix-ветке и проходит проверяемый PR в **develop**. В **main** изменения попадают только после отдельного явного разрешения владельца. Это правило пользователя относится и к начальному наполнению пустого репозитория. Не создавать main, не направлять туда прямой push и не включать автоматическое слияние как способ обойти согласование.

Перед запросом выпуска готовятся состав изменений, конкретные commit SHA, результаты проверок, известные ограничения и план отката. Разрешение на один выпуск не считается разрешением на следующие. Если после согласования существенно изменились состав или проверенный commit, разрешение относится к прежнему результату. Записанное правило процесса не выдаётся за включённую серверную защиту ветки; настройки GitHub и их фактическое состояние проверяются отдельно.

Допускается выпуск завершённых вертикальных частей: сначала доступная методика, затем готовые платные услуги, занятия и курсы. Для каждой публикуемой функции выполняются её условия запуска. Такая последовательность не исключает остальные согласованные продукты из объёма и не разрешает принимать деньги за неготовую услугу.

## Вертикальные задачи и проверки

- [ ] **E13-01. Состав первого выпуска.** Зафиксировать эпики, пользовательские маршруты, версии материалов, тарифы и открытые ограничения. Сопоставить каждый путь с критериями A01–A20 общего плана и локальными AC эпиков. Отметить выполнено, не выполнено или не относится к этому выпуску с причиной.
- [ ] **E13-02. Полный клиентский проход.** Проверить вход, свой профиль, анкету, бесплатный результат и переходы воронки на фактически поддерживаемых клиентах. Для оплаченных продуктов пройти заказ, подтверждение, работу специалиста и доступный результат. Не объявлять отложенный веб-объём или нативные приложения реализованными.
- [ ] **E13-03. Приёмка администратором.** Специалист создаёт, проверяет, публикует и обслуживает сущности каждого выпущенного эпика. Пройти матрицу админки: для каждой сущности доступны требуемые действия и история. Наличие клиентского интерфейса без административного управления не завершает функцию.
- [ ] **E13-04. Деньги, сроки и права.** Воспроизвести дубликаты, задержки, гонки и восстановление на тестовых данных и доступных средах провайдеров. Подтвердить соответствие суммы, валюты и заказа. Отдельно оформить допустимый сценарий реального контрольного платежа с разрешёнными средствами, если он нужен.
- [ ] **E13-05. Медиа, изоляция и восстановление.** Проверить подстановку чужих идентификаторов, истечение ссылки, повторную загрузку и права специалиста. Создать резервную копию, восстановить в изолированной среде и сверить ключевые записи, связи файлов, оплаты, дедлайны и права. Наличие команды backup само по себе не считается восстановлением.
- [ ] **E13-06. Инструкция оператора и откат.** Подготовить действия при сбое ИИ, недоступности Telegram, расхождении платежа, просрочке и отсутствии специалиста. Описать остановку новых продаж, откат приложения, совместимость миграций и сохранение уже принятых обязательств.
- [ ] **E13-07. Проверяемый выпуск.** Собрать release PR develop → main только для подготовленной версии, если main уже существует по разрешённому процессу. До явного разрешения владельца оставить изменения в develop. После разрешения выполнить предусмотренное слияние и отдельную проверку выпуска; не считать слияние автоматическим разрешением на все внешние публикации.

## Управление через админку

Матрица админки становится обязательным условием готовности каждого эпика. Включить управление публикацией контента, продуктов, тарифов и клиентских функций; состояние интеграций; лимиты продаж; очереди и настройки эксплуатации. Исторические оплаты, утверждения и аудит управляются допустимыми операциями, а не свободным редактированием фактов.

Развёртывание кода, миграции и резервное восстановление остаются инженерными процедурами с проверяемым результатом. Это не бизнес-сущности, которые требуется превратить в произвольный редактор команд внутри админки. Администратор должен видеть доступность сервиса и иметь предусмотренные операционные действия без обращения к SQL.

## Проверки приёмки

| ID | Дано / когда | Тогда |
| --- | --- | --- |
| E13-AC1 | Функция готова клиенту, но сущность управляется только из БД | Критерий готовности эпика не выполнен |
| E13-AC2 | Разрешения на main нет; develop проверен | Изменения остаются в develop; слияние в main не выполняется |
| E13-AC3 | Внешний API отказал после подтверждения покупки | Деньги и обязательство сохранены; предусмотрен путь продолжения |
| E13-AC4 | Выпуск включает курс без утверждённого содержания | Его продажи не включаются; задача остаётся открытой |
| E13-AC5 | Резервная копия восстановлена в тестовой среде | Контрольные связи аккаунт → заказ → право/результат воспроизводятся |
| E13-AC6 | Основной ответ опубликован; уточнение пришло своевременно | Соблюдены 24 часа клиенту и отдельные 48 часов специалисту |
| E13-AC7 | Подготовлен протокол приёмки | Фактически выполненные проверки отделены от запланированных |

## Условия выпуска и готовность

Владелец и специалист утверждают материалы и условия продаж; разработчик подтверждает технические проверки. Согласованы платёжные поверхности, хранение и обработка данных, сроки доступа, денежные пограничные случаи и порядок обслуживания. Числовые значения не берутся из примерных цен исходной идеи.

Готовность: есть воспроизводимая версия, проверенные публичные маршруты и админка, протокол приёмки, инструкция эксплуатации и откат. Слияние в main имеет отдельное основание; документация не заявляет выполненных проверок или настроенной защиты без фактического подтверждения.
